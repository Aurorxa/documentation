# UEFI、SHIM 和 Secure Boot（安全启动）

当你在现代计算机上按下电源按钮时，在 Linux 启动之前，一系列复杂的事件就已经开始了。固件（firmware）初始化硬件、发现可引导设备、加载早期引导软件，并最终将控制权移交给操作系统内核。几十年来，这个过程依赖于对执行内容进行很少或不进行验证的固件。这种设计使得早期引导过程成为恶意软件（malware）的有吸引力的目标。UEFI 和 Secure Boot 被引入以解决这个问题。

本文介绍现代 PC 引导架构，并解释 Secure Boot 为何存在。本系列的后续文章将在此基础上构建，探讨 Linux 发行版如何与 Secure Boot 集成。

## 引导过程概览

在深入技术细节之前，了解系统启动的各个整体阶段是有帮助的。

现代引导序列的简化版本如下：

1. 系统上电
2. 固件初始化
3. 硬件发现
4. 引导加载程序（bootloader）发现
5. 引导加载程序执行
6. 操作系统内核加载

每个阶段都以极高的权限运行。如果攻击者能够在此序列的早期插入恶意代码，那么该代码可能控制之后运行的一切。

因此，引导过程是一个关键的安全边界。

## 传统 BIOS 引导

多年来，PC 使用基本输入输出系统，即 BIOS。

BIOS 固件执行硬件初始化，然后尝试将可引导磁盘的第一个扇区加载到内存中。

这个扇区被称为主引导记录（Master Boot Record，MBR）。

主引导记录包含分区表和一小段可执行代码，该代码加载引导加载程序的下一阶段。

该过程大致如下：

1. BIOS 初始化 CPU、内存和硬件设备
2. BIOS 选择一个引导设备
3. BIOS 读取主引导记录
4. MBR 代码加载额外的引导加载程序代码
5. 引导加载程序加载操作系统

这种设计有两个主要局限性。

首先，主引导记录只有 512 字节，严重限制了功能。

其次，BIOS 对其加载的内容不进行任何密码学验证。

如果恶意软件修改了 MBR，固件将不加置疑地执行它。

这种弱点使得一类称为 bootkit 的恶意软件得以产生。

## Bootkit 和早期引导恶意软件

Bootkit 被设计用来感染引导过程的最早阶段。

与在操作系统内部运行的普通恶意软件不同，bootkit 在操作系统内核加载之前执行。

这使得它们特别强大，因为：

- 它们可以对操作系统安全工具隐藏自身
- 它们可以拦截内核加载
- 它们可以在保护措施激活之前修改系统内存

历史上，bootkit 针对的组件包括——主引导记录、引导加载程序代码和固件扩展。

因为 BIOS 不执行签名验证，攻击者只需要对磁盘或固件的写访问权限即可在重启后持久存在。

这些弱点促使业界重新思考引导架构。

## 向 UEFI 的迁移

统一可扩展固件接口（Unified Extensible Firmware Interface，UEFI）取代了传统 BIOS 模型。

UEFI 提供了一个更灵活的固件环境，并引入了在引导期间执行 EFI 应用程序的概念。

UEFI 不再加载一个微小的 512 字节扇区，而是加载存储在专用分区——EFI 系统分区（EFI System Partition）——上的完整可执行文件。

这些文件使用 PE 可执行格式，通常具有 `.efi` 扩展名。

示例包括：

- 引导加载程序，如 GRUB
- 引导管理器（boot manager），如 systemd-boot
- 固件实用工具

!!! note "引导加载程序 vs 引导管理器"

    *引导管理器*负责选择应启动哪个操作系统或引导条目。它展示一个选择菜单并决定启动哪个引导目标。而*引导加载程序*负责将操作系统内核加载到内存中并将控制权转移给它。

    在许多 Linux 系统中，这些角色合并于同一个程序中。例如，GRUB2 可以展示引导菜单（充当引导管理器），然后加载 Linux 内核（充当引导加载程序）。

现代引导流程大致如下：

1. 系统上电
2. UEFI 固件初始化硬件
3. 固件加载配置变量
4. 固件搜索 EFI 引导条目
5. 固件加载一个 EFI 应用程序
6. 该 EFI 应用程序加载操作系统内核

与传统 BIOS 模型相比，这种架构允许更丰富的功能。

然而，它也创造了更大的攻击面。

## EFI 系统分区

UEFI 系统将引导加载程序存储在一个称为 EFI 系统分区的专用分区中。

此分区通常使用 FAT32 格式化，并在 Linux 系统中挂载于 `/boot/efi`。

使用 `tree` 或 `ls` 命令查看 EFI 系统分区的内容：

```
# tree  /boot/efi/
/boot/efi/
└── EFI
    ├── BOOT
    │   ├── BOOTX64.EFI
    │   └── fbx64.efi
    └── rocky
        ├── BOOTX64.CSV
        ├── grub.cfg
        ├── grubx64.efi
        ├── mmx64.efi
        ├── shim.efi
        ├── shimx64.efi
        └── shimx64-rocky.efi
```

你会注意到在 `/boot/efi/EFI/rocky/` 子文件夹下有一些重要的 EFI 可执行文件，如 `shimx64.efi`、`grubx64.efi` 等。因为这些文件由固件直接执行，它们充当关键的安全组件。

这些 EFI 二进制/可执行文件构成了 Linux 引导链的起点。

后续文章将探讨这些文件是如何被签名和验证的。

## 为何引入 Secure Boot

仅有 UEFI 并不会自动使系统安全。

没有验证的情况下，固件仍然会执行它遇到的任何 EFI 二进制文件。

Secure Boot 添加了一个密码学验证步骤。

当启用 Secure Boot 时，固件在执行二进制文件之前会验证 EFI 二进制文件是否由受信任的证书签名。

如果某个二进制文件没有被受信任的密钥签名，固件将拒绝运行它。

此机制建立了一条信任链（chain of trust）的起点，该信任链通过引导加载程序延续，最终到达操作系统内核。

## 信任链的概念

Secure Boot 通过将信任从一个组件扩展到下一个组件来工作。

每个阶段在执行下一个阶段之前对其验证。

过程遵循此模式：

1. 固件验证一个 EFI 应用程序
2. 该 EFI 应用程序验证下一个引导组件
3. 引导加载程序验证操作系统内核

如果任何阶段验证失败，引导过程将停止。

后续文章将详细探讨此信任链如何工作。

## 动手实践：确定你的系统是否使用 UEFI

你可以快速确定一个 Linux 系统是否使用 UEFI 引导。

运行以下命令：

```
ls /sys/firmware/efi
```

如果该目录存在，则系统使用 UEFI 引导。

如果该目录不存在，则系统使用传统 BIOS 模式引导。

## 动手实践：查看 UEFI 引导条目

UEFI 固件存储指向 EFI 可执行文件的引导配置条目。

你可以使用 `efibootmgr` 工具检查它们。

如果需要，先安装它：

```
sudo dnf -y install efibootmgr
```

然后运行：

```
efibootmgr -v
```

这将显示存储在固件中的引导条目以及 EFI 可执行文件的路径。
