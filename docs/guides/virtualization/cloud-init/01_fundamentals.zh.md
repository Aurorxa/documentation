## 首次启动架构

本指南深入探讨 `cloud-init`，它是自动化初始化 Rocky Linux 10 云实例的关键工具。当我们谈论在云端部署服务器时——或者甚至是在本地虚拟化实验环境中——我们通常认为从空白镜像到一台功能齐全、网络就绪的机器几乎是瞬间完成的。这一数字炼金术的壮举由一个不知疲倦的工具完成：cloud-init。

## 1. 启动引导难题

### 问题：当服务器"盲目"启动时

想象一个通用的 Rocky Linux 10 QCOW2 镜像。它是一个完美、原始的副本，不知道自己的最终目的地。它不知道自己的主机名，不知道哪个用户账户应该有 SSH (安全外壳协议) 访问权限，不知道自己在哪个时区，也不知道需要 Apache 还是 Nginx。

如果部署的是物理硬件，系统管理员会手动配置所有这些参数。但在云中，服务器是短暂的，可以成千上万地上下伸缩。我们需要一种标准化、通用且可靠的机制，在镜像首次启动时将必要的上下文注入到那张空白镜像中。

这就是 **cloud-init** 要解决的问题。

### 什么是 cloud-init

简单来说，Cloud-Init 是处理云实例早期初始化的行业标准多发行版软件包。它是负责接收通用镜像（比如我们正在使用的镜像）并执行所需配置任务、将其转变为独一无二、可用于生产环境的服务器的核心服务。

它位于配置过程的核心位置，解释 **元数据** 和 **用户定义的指令** 来设置系统。没有它，你的云实例只是一个编译精美的 Linux 内核，却患有"身份认同危机"。

### cloud-init 生态系统

cloud-init 是一个消费者，而不是创建者。它依赖底层云平台（AWS、Azure、GCP、OpenStack，或本地工具如 libvirt）向其提供配置信息。

* **云提供商** 通过专门的 *数据源*（通常是本地 HTTP 端点、特定的磁盘标签或内核参数）暴露数据。
* **cloud-init** 检测到这个数据源，读取配置，并执行相应的配置步骤。

这种解耦——镜像通用，配置由外部提供——是整个云部署模型的基本精髓。

## 2. Rocky Linux 10 与通用云镜像

在本指南中，我们将使用官方的 [Rocky-10-GenericCloud-Base.latest.x86_64.qcow2](https://dl.rockylinux.org/pub/rocky/10/images/x86_64/Rocky-10-GenericCloud-Base.latest.x86_64.qcow2)。

### 目标镜像：预配置的工作主力

这个镜像很特别，因为它预装了 cloud-init 软件包并已启用。它已经被 *通用化* (generalized)，意味着所有机器特定的标识符、SSH 主机密钥和日志文件都被清除。它已经准备好在首次启动时接收新的身份。

!!! warning "使用推荐的镜像"

    如果你尝试在标准的 Rocky Linux 安装（例如最小化 ISO 安装）上使用 cloud-init，你会发现它默认并不存在。请坚持使用 **通用云镜像**，以避免不必要的复杂性并确保一切按预期工作。尝试使用其他镜像来完成本指南中的练习可能会失败，并且不被支持。

### 核心概念：User-Data vs. Meta-Data

cloud-init 处理的配置信息分为两种关键类型。理解这一区别对于知道你能控制什么以及云提供商控制什么至关重要。

可以把它想象成盖房子：**Meta-Data** (元数据) 是城市分配的街道地址，而 **User-Data** (用户数据) 是你提供的室内设计蓝图。

| 数据类型   | 来源和用途                                                                                                                                    | 配置类型  |
| :---------- | :------------------------------------------------------------------------------------------------------------------------------------------ | :------------------ |
| **Meta-Data** (元数据) | 由云平台提供（只读）。包含系统标识符，如实例 ID、主机名（如果平台提供）、区域和可用区。 | *系统上下文*    |
| **User-Data** (用户数据) | 由用户提供。这是你的指令集——YAML 配置块或 Shell 脚本，用于自定义服务器。                  | *用户指令* |

**Meta-Data** 告诉 cloud-init 它 *在哪里*，**User-Data** 告诉 cloud-init *该做什么*。

我们将主要关注如何编写有效的 **User-Data** 文件，这些文件通常以强制的 YAML 头开始：

```yaml
#cloud-config
```

## 3. 生命周期：cloud-init 的四个初始化阶段

cloud-init 不仅是运行一个脚本然后退出；它执行一系列高度结构化的阶段，与服务器的启动过程对齐。这种方法论确保了依赖关系得到满足（例如，在下载软件包之前先配置网络）。

理解这个生命周期对于调试至关重要，也能让你精确知道你的自定义指令何时被执行。

| 阶段       | 时机和描述                                                                                                                    | 关键动作/模块                                                                                             |
| :---------- | :-------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------- |
| **Generator** (生成器) | 在启动过程的非常早期运行。设置内部目录并执行基本配置检查。 | 内部设置，日志初始化。                                                                             |
| **Local** (本地)     | 在网络尚未就绪时运行。它处理本地数据源，如 CD-ROM 或虚拟驱动器（我们在实验中会用到）。 | 从本地数据设置主机名，初始磁盘设置。                                                           |
| **Network** (网络)   | 在网络完全配置并可操作后运行。它查询基于网络的数据源（如云提供商的 API）。      | 配置网络接口，从网络元数据获取密钥。                                                 |
| **Final** (最终)     | 最后运行。大部分用户定义的配置在此阶段进行，因为所有先决条件（用户、网络、磁盘）现在都已就绪。 | 安装软件包，运行自定义脚本 (runcmd)，写入文件 (write_files)，以及系统清理。 |

!!! tip "检查日志"

    在排除故障时，一定要检查 `/var/log/cloud-init.log`。这个文件是 `cloud-init` 过程的取证报告，精确显示每个阶段何时开始和结束，以及沿途执行了哪些模块。如果你的脚本没有运行，日志会准确地告诉你原因以及哪个阶段失败了。
